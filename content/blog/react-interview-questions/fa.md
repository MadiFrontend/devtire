اگر برای مصاحبه فرانت‌اند آماده می‌شوید، بخش React تقریباً همیشه می‌آید. نه لزوماً به شکل یک لیست حفظی از APIها، بلکه به شکل سوال‌هایی که نشان می‌دهد واقعاً می‌فهمید کامپوننت کی رندر می‌شود، state کجا باید زندگی کند و وقتی صفحه کند شد از کجا شروع می‌کنید.

این مطلب لیست «۱۰۰ سوال React» نیست. روی چیزهایی تمرکز می‌کند که در مصاحبه‌های واقعی زیاد می‌شنوم، جواب قابل قبول برای هر سطح چیست، و کجاها کاندیداها معمولاً می‌سوزند. برای تمرین مستقیم هم لینک کوییزهای [React](/fa/frontend/react) و [مدیریت state](/fa/frontend/state-management) را گذاشته‌ام.

## مصاحبه React معمولاً چه شکلی است؟

بسته به شرکت فرق دارد، ولی الگوی رایج این است:

1. چند سوال مفهومی پشت سر هم (۱۰ تا ۲۰ دقیقه).
2. یک تسک live coding کوچک: مودال، autocomplete، لیست با فیلتر، فرم چندمرحله‌ای.
3. گاهی بحث کوتاه درباره یک باگ performance یا یک تصمیم معماری.

مصاحبه‌کننده معمولاً دنبال سه چیز است: آیا مدل ذهنی درستی از React دارید، آیا می‌توانید با صدای بلند فکر کنید، و آیا وقتی گیر می‌افتید مسیر درستی برای پیدا کردن جواب دارید یا فقط حدس می‌زنید.

## مبانی که بدون آن‌ها جلو نمی‌روید

### کامپوننت، props و state

سوال کلاسیک: «فرق props و state چیست؟»

جواب کوتاه و درست: props از بیرون می‌آید و مالک آن والد است. state متعلق به خود کامپوننت است و تغییرش باعث رندر دوباره می‌شود. props را داخل فرزند تغییر نمی‌دهید؛ اگر لازم است تغییر کند، callback به والد می‌فرستید.

سطح بالاتر: بگویید state محلی باید نزدیک جایی باشد که استفاده می‌شود. اگر state را خیلی بالا نگه دارید، رندرهای اضافه می‌گیرید. اگر خیلی پایین نگه دارید، اشتراک‌گذاری سخت می‌شود. این trade-off را بلد باشید.

### Virtual DOM و reconciliation

خیلی‌ها می‌گویند «Virtual DOM سریع‌تر از DOM واقعی است» و همان‌جا متوقف می‌شوند. این جواب ناقص است.

React با Virtual DOM یک توصیف از UI می‌سازد، آن را با نسخه قبلی مقایسه می‌کند و فقط تغییرات لازم را روی DOM واقعی اعمال می‌کند. هزینه اصلی معمولاً کار JavaScript و commit روی DOM است، نه «جادوی Virtual DOM». اگر مصاحبه‌کننده عمیق‌تر رفت، درباره fiber، interruptible rendering و اینکه چرا key در لیست‌ها مهم است حرف بزنید.

### کلیدها (keys)

سوال: «چرا در لیست‌ها به key نیاز داریم و چرا index گزینه بدی است؟»

key به React کمک می‌کند بفهمد کدام آیتم همان آیتم قبلی است. اگر از index استفاده کنید و ترتیب لیست عوض شود (حذف، اضافه، sort)، React ممکن است state کامپوننت اشتباهی را به آیتم دیگری بچسباند. مثال کلاسیک: input داخل ردیف لیست که بعد از حذف یک آیتم، مقدار اشتباه نشان می‌دهد.

برای تمرین این بخش: [سوالات React جونیور](/fa/frontend/react/junior).

## Hooks: جایی که بیشتر آدم‌ها گیر می‌کنند

### useState

غیر از سینتکس، این‌ها را بلد باشید:

- آپدیت state ناهمزمان دسته‌بندی می‌شود. اگر بر اساس مقدار قبلی آپدیت می‌کنید، از فرم تابعی استفاده کنید: `setCount(c => c + 1)`.
- اگر state یک object است، باید نسخه جدید بسازید. mutation مستقیم (`state.items.push(...)`) تشخیص داده نمی‌شود.
- اگر مقدار اولیه محاسبه سنگینی دارد، از lazy initializer استفاده کنید: `useState(() => compute())`.

### useEffect

این یکی هنوز پرتکرارترین منبع باگ در مصاحبه است.

سوال‌های رایج:

- آرایه وابستگی خالی یعنی چه؟
- چرا infinite loop رخ می‌دهد؟
- cleanup برای چیست؟
- چرا نباید همه data fetching را بدون فکر داخل effect انداخت؟

جواب تمیز: effect یعنی «بعد از اینکه UI با این dependencies هم‌تراز شد، این کار جانبی را انجام بده». cleanup وقتی لازم است که subscription، timer یا listener ساخته‌اید. اگر dependency را فراموش کنید، با مقدار کهنه کار می‌کنید. اگر object یا function ناپایدار در dependency بگذارید، effect بی‌خودی تکرار می‌شود.

نکته‌ای که سینیورها اضافه می‌کنند: خیلی از data fetchingها امروز بهتر است با مکانیزم‌های framework (مثل loaderها یا Server Components) یا کتابخانه‌هایی مثل TanStack Query مدیریت شوند، نه با یک `useEffect` خام در هر صفحه.

تمرین: [React میدل](/fa/frontend/react/middle).

### useMemo، useCallback و React.memo

سوال محبوب: «کی از این‌ها استفاده می‌کنید؟»

جواب ضعیف: «همه‌جا، برای performance.»

جواب خوب: فقط وقتی هزینه محاسبه یا رندر فرزند واقعاً محسوس است، یا وقتی referential equality برای dependency یک effect مهم است. memoization خودش هزینه دارد و کد را شلوغ می‌کند. اول با Profiler اندازه بگیرید، بعد بهینه کنید.

`React.memo` وقتی کمک می‌کند که props پایدار باشند. اگر هر رندر والد، object یا function جدید می‌سازد، memo عملاً بی‌اثر می‌شود. اینجاست که `useCallback` معنی پیدا می‌کند، نه به‌عنوان عادت پیش‌فرض.

### useRef

useRef برای نگه داشتن مقداری است که بین رندرها می‌ماند ولی باعث رندر دوباره نمی‌شود. کاربردهای رایج: دسترسی به DOM، نگه داشتن id تایمر، و ذخیره مقدار قبلی.

سوال خوب مصاحبه: «فرق useRef و useState چیست؟» اگر فقط بگویید «یکی برای DOM است»، ناقص جواب داده‌اید.

## رندر و performance

این بخش معمولاً مرز میدل و سینیور را مشخص می‌کند.

سناریوی پرتکرار: «یک لیست بلند داریم. با هر تایپ در سرچ‌باکس، کل صفحه کند می‌شود. چه می‌کنید؟»

مسیر جواب معقول:

1. اول اندازه‌گیری (React Profiler، چه چیزی رندر می‌شود).
2. state سرچ را پایین‌تر بیاورید تا کل درخت آپدیت نشود.
3. ردیف‌ها را در صورت نیاز memo کنید.
4. برای لیست خیلی بزرگ، virtualization را در نظر بگیرید.
5. اگر تایپ سنگین است، `useDeferredValue` یا debounce را بررسی کنید.

جواب بد: بلافاصله `useMemo` پاشیدن روی همه چیز بدون تشخیص مشکل.

سوال‌های مرتبط دیگر:

- Context باعث رندر همه consumerها می‌شود؛ چطور محدوده را کوچک می‌کنید؟
- چه فرقی بین state سرور (cache داده) و state کلاینت (UI) هست؟
- کی state را به URL می‌برید؟

برای این لایه: [React سینیور](/fa/frontend/react/senior) و [مدیریت state](/fa/frontend/state-management).

## Controlled در برابر uncontrolled

سوال ساده‌ای که هنوز اشتباه جواب داده می‌شود.

در controlled، منبع حقیقت state ری‌اکت است (`value` + `onChange`). در uncontrolled، DOM خودش مقدار را نگه می‌دارد و شما با ref می‌خوانید.

Controlled برای فرم‌های پیچیده، validation لحظه‌ای و همگام‌سازی چند فیلد بهتر است. Uncontrolled گاهی برای فرم‌های ساده یا integrate با کتابخانه‌های غیرری‌اکتی سبک‌تر است. هیچ‌کدام «همیشه درست» نیستند؛ باید بگویید چرا یکی را انتخاب می‌کنید.

## Composition بهتر از inheritance و prop drilling بی‌حد

React inheritance ندارد به سبک کلاس‌های کلاسیک UI، و این خوب است. الگوهای رایج:

- children و composition
- compound components
- custom hooks برای اشتراک منطق
- Context برای داده‌ای که واقعاً سراسری است

Prop drilling تا دو سه سطح معمولاً مشکلی نیست. وقتی دردناک شد، قبل از آوردن Redux از خودتان بپرسید: آیا مشکل واقعاً اشتراک state است یا فقط ساختار کامپوننت بد است؟

## سوال‌هایی که در ۲۰۲۶ بیشتر دیده می‌شوند

مصاحبه‌ها کم‌کم از «lifecycle متدهای کلاس» فاصله گرفته‌اند و به این سمت آمده‌اند:

- **Server Components در برابر Client Components**: چه چیزی باید روی سرور بماند، چه چیزی باید `"use client"` باشد، و چرا همه چیز را کلاینت نمی‌کنید.
- **Suspense و streaming**: مرز loading کجا باشد.
- **Transitions**: `startTransition` و `useTransition` برای آپدیت‌های غیرضروری فوری.
- **Cache و data fetching**: stale data، invalidation، و جلوگیری از waterfall.
- **Accessibility در کامپوننت‌ها**: فوکوس در مودال، کیبورد، نقش‌های ARIA فقط وقتی لازم است.

لازم نیست روی همه این‌ها متخصص باشید. ولی اگر برای نقش میدل به بالا می‌روید، دست‌کم باید بتوانید با مثال واقعی حرف بزنید، نه فقط تعریف حفظی.

اگر مسیرتان Next.js است، این‌ها را هم در [سوالات Next.js](/fa/frontend/nextjs) ببینید، چون خیلی از مصاحبه‌های React امروز عملاً مصاحبه React + framework هستند.

## جواب‌هایی که امتیازتان را می‌سوزاند

- «Virtual DOM همیشه سریع‌تر است.» بدون توضیح.
- «useEffect برای هر چیزی که بعد از mount لازم است.» یعنی مدل ذهنی side effect ندارید.
- «Context جایگزین Redux است.» گاهی بله، گاهی نه؛ بستگی به نرخ آپدیت و پیچیدگی دارد.
- «همه چیز را memo می‌کنم تا سریع شود.» معمولاً یعنی هنوز اندازه‌گیری نکرده‌اید.
- حفظ کردن نام API بدون مثال. مصاحبه‌کننده سریع می‌پرسد: «آخرین بار کجا به این باگ خوردی؟»

اگر تجربه‌تان کم است، دروغ نسازید. بگویید این را در پروژه تمرین کرده‌اید یا در مستندات خوانده‌اید، بعد استدلالتان را نشان دهید. صداقت به‌علاوه فکر کردن بلند، از ادای تجربه قوی‌تر است.

## چطور در یک یا دو هفته جمعش کنید

اگر وقتتان کم است، این ترتیب را پیشنهاد می‌کنم:

**روزهای ۱ و ۲:** props، state، لیست‌ها، keys، controlled inputs. کوییز جونیور را تا وقتی اشتباه‌های تکراری‌تان کم شود بزنید.

**روزهای ۳ تا ۵:** useEffect، dependency array، cleanup، data fetching، و یک کامپوننت واقعی مثل search box با debounce.

**روزهای ۶ تا ۸:** رندر، memoization، Context، و یکی دو سناریوی performance. کوییز میدل.

**روزهای ۹ و ۱۰:** یک live coding کامل زمان‌دار (۴۵ دقیقه). بعد همان کد را نقد کنید: کجا state بد قرار گرفته، کجا effect اضافی دارید، کجا accessibility جا افتاده.

**اگر برای سینیور می‌روید:** دو جلسه اضافه برای معماری state، مرز server/client، و توضیح trade-offها. کوییز سینیور را جدی بگیرید، حتی اگر بعضی سوال‌ها سخت بودند؛ همان‌ها نقطه ضعف را نشان می‌دهند.

## جمع‌بندی

مصاحبه React کمتر از آن‌که فکر می‌کنید درباره حفظ کردن API است، و بیشتر درباره این است که وقتی UI خراب یا کند می‌شود، آیا مدل درستی در سرتان دارید یا نه. رندر، state، effectها و اندازه‌گیری را درست بفهمید؛ بقیه روی این اسکلت سوار می‌شوند.

اگر فقط یک کار انجام می‌دهید، امروز ۲۰ سوال از کوییز React را با توضیح کامل بخوانید، نه فقط گزینه درست را. همان توضیحات معمولاً همان چیزی هستند که در مصاحبه باید با زبان خودتان بگویید.
